hardware-lib 8.2.0 + mqtt-lib 2.7.0

Release notes for the Android app8 October 2026cumulative against the fleet's 8.0.0 / 2.6.0GitHub release v8.2.0
What you have to do
  • Swap both AARs in libs/ and rebuild. No code change is required. Both libraries are additive; an app built on 8.0.0 / 2.6.0 compiles and behaves the same.
  • Optional code, only to use the new parts: RS232 vend events through the existing VendListener, and a ready-feedback gate on more than one digital input. Steps are in the handoff README, section "Android: what changes from 8.0.0 to 8.1.0 / 2.7.0".
  • Two switches operators turn on per machine from the dashboard, nothing for the app: Force End (new in 8.2.0) closes the session after every vend success on machines that never send SESSION COMPLETE; Direct Vend now also reports ENABLED_STATE so the health-check screen passes on machines that never send READER ENABLE.

New in 8.2.0: force session end after vend

operator switch, no code change

Field case: a machine keeps the session open after VEND APPROVED and VEND SUCCESS and never sends SESSION COMPLETE, so the reader never gets to send END SESSION and the next customer cannot start.

Persisted setting force session end, default OFF. When ON, as soon as VEND SUCCESS is acknowledged the reader arms SESSION CANCEL REQUEST for the next POLL; the machine answers SESSION COMPLETE and the session closes with END SESSION as usual. A failed vend keeps the spec flow. Nothing extra is sent if SESSION COMPLETE already arrived. The VendListener callbacks are unchanged.

  • Dashboard: Force End toggle next to Direct Vend. Remote: setForceSessionEnd:on|off.
  • Kotlin: HardwareLib.setForceSessionEnd(Boolean) and isForceSessionEnd. getSettings reports forceSessionEndAfterVend.
  • Log: [mdb] force session end: SESSION CANCEL REQUEST goes out on the next POLL (after VEND SUCCESS).
  • Also: when END SESSION goes out every per-session flag is cleared, so a forced cancel or a late approve can never leak into the next session.

hardware-lib 8.1.0

additive, no breaking change

RS232: rules can fire the VendListener

A rule may carry "event": vendRequest, vendSuccess, vendFailure or vendCancel. On match the same three callbacks the MDB engine uses fire: onVendRequest(amount, minorUnits, -1) with the price the rule extracted, then exactly one onVendSuccess or onVendFailure (reason FAILED for vendFailure, CANCELLED_BY_VMC for vendCancel). PRODUCTION FAIL after a paid sale now reaches the app as onVendFailure instead of a log line. Rules without event behave exactly as before. The app still answers the machine with Rs232Lib.sendHex or sendXorFrame.

{"setRs232Rules":[

  {"name":"PRODUCTION_OK",  "rx":"A0 03 00 07 53 55 43 43 45 53 53 E7","tx":"","event":"vendSuccess"},
  {"name":"PRODUCTION_FAIL","rx":"A0 03 00 06 46 41 49 4C 45 44 A6","tx":"","event":"vendFailure"},

Pulse: ready feedback on several inputs

PulseLib.setReadyFeedbackChannels(mapOf(0 to 1, 2 to 0)), or remote setReadyFeedback:0=1,2=0. Every listed input must show its ready value before a pulse train goes out. The old single-channel setReadyFeedback(value, channel) and setReadyFeedback:yes,value,channel still work. getSettings adds readyFeedbackChannels.

MDB: direct vend reports ENABLED_STATE

With setDirectVend(true) the state listener and VMC_STATUS.state say ENABLED_STATE while the bus is INACTIVE or DISABLED. The real state is in VMC_STATUS.busState. Fires immediately when direct vend is switched on, returns to the real state when switched off.

Everything else, the MDB engine, the three-callback VendListener and every remote command, is unchanged.

mqtt-lib 2.7.0

no code change

Field case D-0130: the status topic flipped online and offline every 3 seconds. That pattern, online for 3.1 s and offline for 60 ms, is two live sessions sharing one client id and kicking each other, not a network fault.

  • Stable client id per process. The id is now <deviceId>-<random> and reused on every reconnect. Before, each reconnect took a new id, so after a drop the broker kept the old half-open session alive for up to 45 s with its Will armed, and that late Will wrote a retained offline over the new session's online. A clientId the app passes in MqttConfig is used exactly as given. Never share one id between two live clients.
  • Graceful stop sends DISCONNECT after the retained offline, so the broker does not fire the Will on top of it.
  • Reconnect backoff with jitter: 3, 6, 12, 24, 48, 60 s instead of a flat 3 s, back to 3 s after a session lasts 30 s.
  • Connection counters since app start: sessions established, connection losses, failed connect attempts, short sessions in a row, last loss reason. Every reconnect logs one line, for example [mqtt] reconnected as D-0130-3f2a - session #7, losses=6, failed attempts=0, ..., plus MQTT_STATS:{...}. Three short sessions in a row log a WARNING naming the client id. New command mqttStats. version now also prints the client id and the counters. The dashboard shows them in a link badge.

Known limits

read before the field test
  • Not yet run on a real CM30. Compiled, API-checked with javap and dex-checked. D-0130 is the first field check.
  • The dashboard's Ready FB control is still single-channel. Use setReadyFeedback:0=1,2=0 on the passthrough bar for multi-input.
  • Force End acts on VEND SUCCESS only. A machine that sends neither VEND SUCCESS nor VEND FAILURE after approval needs a different fix, a timeout; send a log of one sale if you see that.
  • RS232 has no approve or deny command. The app answers the machine with bytes, as before.
