Release notes - hardware-lib 8.2.2 + mqtt-lib 2.8.0

Release: https://github.com/H2-designs/Hardware-Library/releases/tag/v8.2.2 (company copy: https://github.com/RabbahSystems/hardware-library/releases/tag/v8.2.2) Date: 22 October 2026. Replaces v8.2.1 (15 October). Cumulative against the fleet's hardware-lib 8.0.0 / mqtt-lib 2.6.0.

TL;DR for the Android app

  • Swap both AARs: hardware-lib-8.2.2.aar and mqtt-lib-2.8.0.aar. Rebuild. No API change.
  • One behaviour change you must know: your own cancelVend() no longer comes back as onVendFailure. Delete any branch that handled CANCELLED_BY_APP; handle the decline where you call cancelVend().
  • One thing to check in your handler: reverse the charge on FAILED, SESSION_ENDED and RESET when you had approved, not only on FAILED. VENDLISTENER-README.md has the complete handler; SESSION-ENDED-README.md explains why.
  • New: vendStats counters (dashboard Vend button), including how many times a listener callback got stuck.
  • mqtt-lib 2.8.0: the backend's logs topic carries only coded items; plain lines and control lines move to devices/<id>/ops. The device.log.unknown_source flood (D-0554) stops without touching the Logs toggle. Update the dashboard to v8.2.2 with it.
  • RS232 Loyalsuns protocol v2: PRODUCTION_OK / PRODUCTION_FAIL rules now ACK the making result. Rule table only.

New in 8.2.2 (22 October)

Your own cancelVend() is no longer echoed as onVendFailure

Until 8.2.1 HardwareLib.cancelVend() (and the dashboard's cancelVend) closed the open vend and fired onVendFailure with reason CANCELLED_BY_APP, so the app heard its own cancel back. Now a cancel the app asked for closes the vend silently: the deny reply still goes out on the next POLL, lastVendFailureReason still records CANCELLED_BY_APP, no callback. Log: [mdb] vend closed by cancelVend - no onVendFailure (the app's own decision).

Everything the machine does still reaches the listener exactly once: VEND CANCEL / READER CANCEL (CANCELLED_BY_VMC), VEND FAILURE (FAILED), a session closed with the vend open (SESSION_ENDED), RESET / stop() (RESET).

mqtt-lib 2.8.0 - the backend's log topic carries only coded items; everything else goes to ops (8.2.2 release)

Field case D-0554: a device with the dashboard Logs toggle on published every plain report line and every control line to devices/<id>/logs, and the backend filed them as device.log.unknown_source, thousands a day. Turning the toggle off is not an answer: it also stops the coded exchange items the Android/backend team needs.

Since mqtt-lib 2.8.0 MqttLib.enqueue routes by payload: a coded log envelope (RABBAH_LOG:{...} or bare JSON) goes to the log topic as before; everything else - plain [mdb] / [remote] / [app] lines, the control lines (VMC_STATUS, SETTINGS_JSON, CONFIG_JSON, MQTT_STATS, VEND_STATS, RS232_RULES_JSON), PONG, the version reply - goes to devices/<id>/ops (MqttConfig.opsTopicSuffix, default "ops", null = old behaviour). The backend never sees a non-JSON payload on logs again, whatever the toggle says. The Logs toggle keeps its meaning and its persistence. The Hardware Dashboard v8.2.2 subscribes to ops as well; an older dashboard would still decode the coded items but miss the plain lines, so update it with the libraries. No app change, no backend change.

Vend counters - vendStats

Since app start, not persisted. Remote vendStats (dashboard Vend button) answers VEND_STATS:{...} and one readable line: vend requests, successes, failures and failures per reason, app cancels, ignored approves, callbackStuck (a VendListener callback still running after 3 s, with its name and when), callbacks that threw, events with no listener, whether a listener is registered, whether a vend is open. The watchdog line now reads [mdb] WARNING: VendListener.onVendRequest has been running for 3000 ms (stuck #N) .... Code: HardwareLib.vendStatsJson(), vendRequestCount, vendSuccessCount, vendFailureCount, vendFailuresByReason, vendCallbackStuckCount.

RS232: Loyalsuns protocol v2 making-result ACK

The reader must answer Making Success / Making Failed with A1 03 00 02 4F 4B A4. The PRODUCTION_OK and PRODUCTION_FAIL rules carry that tx in every sample table (guide, README, template, samples). Rule table only, no library change. Send the table once from the dashboard; it is persisted.

Since 8.0.0 - 8.2.1 / mqtt-lib 2.7.1 (15 October)

  • Every exchange reaches the backend exactly once (D-0961): add*Listener ignores a repeat registration of the same instance, attachRabbahMqtt() is the complete bridge, RabbahLog drops an identical item within 30 ms.
  • Health check that can never get stuck: the reported state is held and replayed to any state/status listener on registration, re-announced on every real transition, re-sent every 5 s under direct vend while the bus is INACTIVE/DISABLED; currentState = reported state, busState = real.
  • SESSION COMPLETE / VEND CANCEL / SUCCESS / FAILURE answered in every state; a stray SESSION COMPLETE gets END SESSION; RESET wipes every per-session flag; READER ENABLE / CANCEL answered in INACTIVE with direct vend ON.

Since 8.0.0 - 8.2.0 and 8.1.0 (October)

  • 8.2.0 force session end after vend (setForceSessionEnd:on|off, dashboard Force End).
  • 8.1.0 RS232 rules carry "event" and fire the same VendListener; ready-feedback gate on several inputs (setReadyFeedback:0=1,2=0); direct vend reports ENABLED_STATE.

Since 2.6.0 - mqtt-lib 2.7.0 / 2.7.1

Stable client id per process (D-0130 presence flapping), DISCONNECT on stop, reconnect backoff with jitter, connection counters (mqttStats, dashboard link badge), RabbahLog 30 ms dedupe.

Known limits

  • Not yet run on a real CM30. Compiled, API-checked (javap) and dex-checked. First field checks: the no-echo cancel, the counters after a day, D-0961 duplicates, the direct-vend health check, a reader restart mid-session.
  • The dashboard's Ready FB control is still single-channel; use setReadyFeedback:0=1,2=0 on the passthrough bar.
  • Force End acts on VEND SUCCESS only.
  • RS232 has no approve/deny command; the app answers the machine with bytes.
  • simulateExchange exercises the log pipeline only, not the VendListener; use the RS232 bench test in VENDLISTENER-README.md section 8 to exercise the handler without a machine.
