VendListener and the other listeners - how they work inside hardware-lib

hardware-lib 8.2.15, 16 November 2026. This is the mechanics document: how a bus frame becomes a callback, which flags decide it, what approveVend() and cancelVend() really do, why a callback is sometimes delayed, what is guaranteed, and how every other listener (log, exchange, state, status, control, RS232 events, log sink, MQTT) is fed. VENDLISTENER-README.md is the copy-ready implementation (Kotlin, Java, React Native) and the list of field mistakes; MDB-README.md is the whole-library overview; CANCEL-FLOW-README.md and SESSION-ENDED-README.md go deeper on two of the failure paths.

The var slots hold one listener each; assigning again replaces silently. The add… lists hold any number and never deduplicate, so register once per process and remove with the same reference. A listener that throws is caught and skipped, never fatal to the others.

2. The VendListener contract

interface VendListener {
    fun onVendRequest(amount: Double, minorUnits: Int, itemNumber: Int) {}
    fun onVendSuccess(itemNumber: Int) {}
    fun onVendFailure() {}                                        // legacy, no reason
    fun onVendFailure(reason: VendFailureReason) { onVendFailure() }   // 8.2.6: override this one
}
  • onVendRequest is the question: the customer selected an item at this price. The app answers later with approveVend() or cancelVend(); the bus keeps being ACKed meanwhile (the MDB "answer on a later POLL" pattern, and the machine's max response time is 232 s).
  • onVendSuccess is the only "money is earned" event: the machine confirmed the product came out.
  • onVendFailure(reason) is every other end of a vend. One of six reasons:
reasonwho ended itwire event
CANCELLED_BY_VMCthe machineVEND CANCEL 13 01, READER CANCEL 14 02, a new VEND REQUEST while one was open, RS232 rule vendCancel
CANCELLED_BY_APPthe app's own cancelVend()SESSION CANCEL REQUEST or VEND DENIED on the next POLL
CANCELLED_BY_OPERATORdashboard / remote cancelVendsame
FAILEDthe machine after approvalVEND FAILURE 13 03, RS232 rule vendFailure
SESSION_ENDEDthe machine closed the session with the vend openEND SESSION went out on a POLL (after SESSION COMPLETE or READER DISABLE)
RESETthe bus or the appRESET 10, or HardwareLib.stop()

The invariant: every onVendRequest is followed by exactly one onVendSuccess or one onVendFailure, never both, never neither, in that order. Sections 4 to 6 show how the code enforces it.

3. From bus frame to callback

 bus thread                         |  notifyVend()                      |  vend delivery thread (one, FIFO)
 ---------------------------------- | ---------------------------------- | ----------------------------------
 frame arrives from the vendor port |                                    |
 decide + send the reply (ACK ...)  |                                    |
 set / clear the vend flags         |                                    |
 notifyVend("onVendRequest") -----> | count it, flush a held failure     |
                                    | (onVendFailure only) cancel grace? |
                                    |   yes: hold it `delayMs`, return   |
                                    |   no:  deliverVend() ------------> | wait for the vend event gap
                                    |                                    | start the 3 s watchdog
 back to the next frame             |                                    | call the listener (try/catch)
                                    |                                    | cancel the watchdog
  1. Bus thread. Reads one frame, picks the reply, writes it, updates the flags (section 4), and calls notifyVend with the callback name and a lambda. Nothing on this thread waits for the app.
  2. notifyVend. Increments the counter (vendRequests / vendSuccesses / vendFailures). For a request or a success it first flushes any failure still being held by the cancel grace, so a held failure can never land after the next request or after a success. If no listener is set, noListener is counted and the event is dropped. For a failure that arrives inside the cancel grace window it schedules the delivery delayMs later (section 6.1). Otherwise it calls deliverVend.
  3. deliverVend. Submits to vendCallbackExecutor, a single thread. Inside: sleep until the vend event gap since the previous callback *started* has passed (section 6.2), record the start time, arm a watchdog that logs WARNING: VendListener.X has been running for 3000 ms (stuck #n) and counts callbackStuck if the callback is still inside after 3 s, run the lambda, catch any Throwable (callbackThrew), cancel the watchdog.

Because there is exactly one delivery thread and events enter it in the order the bus produced them, the app sees request, then outcome, for every vend, and never two callbacks at once.

A VEND CANCEL, VEND FAILURE or SESSION COMPLETE arriving outside VEND_STATE (a machine finishing a session after the reader restarted) is ACKed and logged as stray; the reader has no vend open, so no callback.

5.4 A new request wipes the old vend (8.2.9)

clearPreviousVend("VEND REQUEST") runs before the new request is armed:

  1. a vend still open -> abortOpenVend(CANCELLED_BY_VMC) (the machine abandoned it by starting another), so the app gets the old failure before the new request, in order on the one thread;
  2. an approval nothing consumed -> dropped (it must not approve the new item at the old price);
  3. a cancel reply still armed -> dropped (it must not deny the new vend);
  4. a pending END SESSION -> dropped (the machine kept the session).

Each drop is logged and counted in requestSupersededFlags.

6. The timing rules

6.1 Cancel grace (8.2.7, defaults 200 / 500 ms since 8.2.10)

Problem: a customer who presses cancel within a few hundred milliseconds of selecting produces onVendRequest and onVendFailure so close together that the app's UI thread draws the request *after* the failure already reset the screen, leaving a stuck "paying" screen.

Rule, in notifyVend: if the callback is onVendFailure and it comes less than cancelGraceWindowMs after the last onVendRequest, it is held and delivered cancelGraceDelayMs later (failureDelayed counted, one log line). The hold is released early, in order, when the next onVendRequest or onVendSuccess arrives (flushHeldFailure), so a held failure never lands after a later event. The hand-over and the enqueue happen under one lock (8.2.12) so a request flushing at the same instant cannot slip its own callback in first. The wire side is not delayed at all: the cancel reply still goes out on the next POLL.

Off with setCancelGrace(0, 0) or setCancelGrace:off; each value 0-5000 ms.

6.2 Vend event gap (8.2.11, default 500 ms)

In deliverVend, before the listener is called: wait until at least vendEventGapMs have passed since the previous callback started. One thread, FIFO, so the wait spaces every pair of events and keeps the order. A screen drawn for one event is on screen for at least the gap before the next event. eventsSpaced counts the waits.

Off with setVendEventGap(0) / setVendEventGap:off; 0-5000 ms.

6.3 Watchdog (3 s)

The listener must return at once and do gateway work on its own thread. A callback still running after 3 s is logged as stuck and counted (callbackStuck, lastStuckCallback, lastStuckAgoSec). Nothing is killed, but every later callback waits behind it, so a stuck request handler delays its own outcome.

7. approveVend() and cancelVend() inside

7.1 approveVend()

if (!vendRequestReceived)               -> false, approveIgnored   ("no VEND REQUEST pending")
if (sessionCancelPending || endSessionPending) -> false, approveAfterCancel ("the vend is over - void / reverse")
vendApprovePending = true               -> true, "VEND APPROVED goes out on the next POLL"

It never queues for a future request, so it can never auto-approve the next customer. A false means the machine will not dispense: the app must void the hold, never capture.

7.2 cancelVend() / cancelVend(response)

if (mdbState != VEND_STATE)             -> false ("no session live")
pendingCancelResponse = response (or the standing cancel mode)
sessionCancelPending = true; vendApprovePending = false
if (vendOpen) abortOpenVend(CANCELLED_BY_APP)          // CANCELLED_BY_OPERATOR from the dashboard
-> true

Works before a request too (abort a session before the customer picks), in which case nothing is open and no callback fires. The two responses: SESSION CANCEL REQUEST (machine answers SESSION COMPLETE, reader then sends END SESSION, session over) or VEND DENIED (session stays open, machine may request again).

7.3 What the next POLL carries in VEND_STATE, in priority order

  1. endSessionPending -> END SESSION: state -> ENABLED, every flag cleared, auto mode re-arms BEGIN SESSION after the cooldown, abortOpenVend(SESSION_ENDED) if a vend was still open.
  2. sessionCancelPending -> SESSION CANCEL REQUEST (and the retry timer is armed) or VEND DENIED; request + approve flags cleared.
  3. vendApprovePending && vendRequestReceived -> VEND APPROVED at priceHigh priceLow; flags cleared.
  4. a session-cancel retry is due -> SESSION CANCEL REQUEST again (up to the count).
  5. otherwise ACK (idle).

So an approval and a cancel armed in the same POLL interval always resolve to the cancel.

8. What the library guarantees

  • Exactly one success or failure per request, in order, on one thread, never on the bus thread.
  • approveVend() cannot charge the next customer: it arms only for a pending request, is refused once a cancel or session end is armed, and is dropped by the cancel-reply POLL, VEND FAILURE, SESSION COMPLETE, READER DISABLE, END SESSION, RESET and the next VEND REQUEST.
  • No onVendSuccess for a vend that already got onVendFailure.
  • One open vend at a time: a new request closes the previous one first.
  • A failure within the grace window is delayed, never dropped, and never delivered after a later request or success.
  • Two callbacks are never closer than the event gap.
  • Settings that change the wire flow (session mode, cancel mode, direct vend, force end, retry, level) never change the three callbacks or their order.
  • The bus reply never waits for the app: ACKs go out while the app thinks.

10. The other listeners, in detail

10.1 Log lines - logListener, addLogListener

Every report(line, showOnScreen) in the library fans out to the single slot and the list, on the offload thread. showOnScreen=false marks per-POLL noise (idle ACKs, unhandled frames when visibility is on): never append those to a growing text view. Prefixes: [mdb], [app], [remote], [rs232], [pulse]. MQTT logging (setMqttLogging) does not affect local listeners, only what leaves the device.

10.2 Exchanges - exchangeListener, addExchangeListener

After the reply bytes have gone out, the bus thread queues queueExchange(cmd, sent); the offload thread classifies the frame into one MdbCmd (codes 110-136, append-only), fills the template message, and delivers one MdbExchangeEvent. Fields: cmd, code, logEventName (e.g. MDB_VEND_REQUEST), rxHex, txName, params (price, item, level where applicable), message, sessionId, publishRemote, showOnScreen, timestampMs. Suppressed exchanges (idle POLL, unhandled with visibility off) still reach this feed with showOnScreen=false; honour publishRemote / showOnScreen if you forward them. Through attachRabbahMqtt each event becomes one coded RABBAH_LOG item on the logs topic.

10.3 State - stateListener, addStateListener

Edge-triggered: the plain state name on every real transition. The reported state is delivered: with direct vend ON, INACTIVE and DISABLED are reported as ENABLED_STATE so an app that waits for "ready" does not wait forever on a machine that never sends READER ENABLE. Since 8.2.1 a listener gets the current state once at registration, on the caller's thread, and while direct vend fakes ENABLED the state is re-sent every 5 s to local listeners (never over MQTT).

10.3.1 Machine ready - readyListener, addReadyListener, isMachineReady, machineReadyJson() (8.2.15)

The question the state listener answers indirectly, answered directly and idempotently: "can the machine sell through this reader right now?". It exists because of one field report: the machine finished its handshake before the Android app registered anything, and the app never learned it was ready. The state listener replays on registration (8.2.1), but that replay goes to whichever native listener exists at that moment; an app whose own code (or JS side) subscribes later still saw nothing until the next transition, which on a quiet machine never comes.

10.4 Status - statusListener

JSON {"state": reported, "recentActivity": bool} plus "busState" and "directVend": true when the reported state is synthetic. Event-driven only: on every transition, when bus traffic appears or has been silent for 5 s, on start/stop, and once at registration. It is the same payload as the VMC_STATUS: control line the dashboard uses for its state badge and "bus alive" dot.

10.5 Control plane - controlListener, addControlListener

(tag, payload) pairs: SETTINGS_JSON (after init, after every setter, on getSettings), CONFIG_JSON (on getConfig, after a payload change), VMC_STATUS, VEND_STATS (on vendStats), MACHINE_READY (8.2.15: on every readiness change and on getMachineReady), and LOG (plain lines, already gated by setMqttLogging). A late registration gets VMC_STATUS, SETTINGS_JSON and MACHINE_READY at once. A transport bridge forwards LOG as the bare line and everything else as TAG:payload.

10.6 RS232 events - addRs232EventListener

One (eventName, params) per matched serial frame, names 1:1 with mqtt-lib's Rs232LogEvent. While a listener is registered, Rs232Lib keeps its plain [rs232] line local so the wire never carries the same exchange twice. A rule with an event (vendRequest, vendSuccess, vendFailure, vendCancel) additionally drives the same VendListener through rs232VendEvent (section 5), with the same vendOpenFlag and the same reasons.

10.7 attachLogSink(sink)

For an app with its own transport: registers a log listener that forwards every line when MQTT logging is on (and drops [rs232] twins when RS232 events are coded) plus a control listener that forwards every non-LOG tag as TAG:payload. Pair it with handleCommand(text) fed from the app's command channel and a dashboard can see and control the whole library.

10.8 attachRabbahMqtt() / detachRabbahMqtt()

Reflection-only wiring to mqtt-lib (hardware-lib has no compile-time dependency on it). Attach registers: a command listener (handleCommand for every text on the cmd and passthrough topics; unknown commands fall through to the app's own listeners), an exchange forwarder (coded items, RabbahLog.log, session id propagation), an RS232 event forwarder (RabbahLog.rs232), a log listener (lines when MQTT logging is on, [remote] answers always) and a control listener (TAG:payload to the ops topic). Detach removes exactly those and nothing the app registered itself. mqtt-lib calls attach on its first connect when autoAttachHardware is on (default); remote attachHardware / detachHardware do the same.

10.9 Remote control - handleCommand(text)

Not a listener but the inbound half of the same surface: any transport hands the text in, the library answers with [remote] lines and control tags on the feeds above. Returns true when the command was consumed. The full command list is in MDB-README.md section 8.

11. React Native

react-native-mdb registers one VendListener in MdbRnModule and re-emits each callback as a JS event on the React Native bridge: MdbVendRequest {amount, minorUnits, itemNumber}, MdbVendSuccess {itemNumber}, MdbVendFailure {reason}. The ordering and spacing guarantees hold up to the native side; JS receives them in the same order through the event emitter. The other feeds map to MdbStateChanged, MdbStatus, MdbLog, MdbExchange, MdbRemoteCommand. approveVend() / cancelVend() / cancelVendWith(mode) return the same Boolean as promises. Settings for the timing rules: setVendEventGap(ms), getVendEventGap(), setCancelGrace(window, delay), getCancelGrace() (1.4.3), getMachineReady() / onMachineReady / onStateChanged (1.5.0).

1.5.0 (hardware-lib 8.2.15): getMachineReady() resolves the readiness snapshot as an object, onMachineReady(fn) delivers it once right after subscribing and then on every change, and onStateChanged(fn) likewise replays the current state. The native module re-emits the current value to every new JS subscriber (RN calls the module's addListener(eventName) for each subscription), so the order "machine handshake first, JS subscribes later" no longer loses the answer. The pulse isMachineReady() is unrelated: that is the digital-in ready-feedback gate.

12. Testing the mechanics without a machine

  • simulateExchange(hex) runs classify -> template -> log / exchange / control listeners only. It does not run the state machine, so it never fires the VendListener. Use it to prove the plumbing to the dashboard.
  • RS232 rules with event drive the real VendListener through the same vendOpenFlag and notifyVend path; VENDLISTENER-README.md section 8 has a ready rule table and the expected reason for each line.
  • The JVM bus-trace harness (source/MdbSlaveApp/hardware-lib/bus-trace/) runs the real HardwareLib against a fake vendor port and asserts replies, callbacks, order, timing and counters for every scenario in this document: S1-S8 (team's B11 cases), S9-S15 (cancel grace, superseded flags), S16-S18 (event gap timing), S19-S24 (8.2.12 fixes), S25-S27 (warm resume), S28 (cash sale), S29-S31 (machine ready: life cycle, late listener replay, RS232 connect logic). 31 of 31 pass on 8.2.15.
  • Nothing from 8.1.0 onward has yet run on a real CM30.
