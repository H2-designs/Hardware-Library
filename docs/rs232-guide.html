RS232 Card Reader Guide

How the coffee-machine ⇄ card-reader serial protocol maps onto Rs232Lib rules — every frame from the vendor document, the rule table that answers it, and the functions that build replies. hardware-lib 7.13.0.

Two things make this protocol different from a fixed-byte protocol like MDB:

  • The amount is ASCII digit text, not binary bytes — 31 35 30 30 30 30 is the string "150000", the price in minor units. A 35.00 payment is only 4 data bytes, so the frame length varies with the amount.
  • Every frame ends in an XOR CRC — Start ^ CMD ^ Length ^ each Data byte. The library computes it for you on replies, and with setCrcCheck(true) it also validates it on every received frame: a bad-CRC frame is discarded with no reply and no listeners, exactly as the document requires.

2 · The rule tableReady to paste

This maps every command in the document. Load it with setRulesJson, from the dashboard as {"setRs232Rules":[…]}, or paste it into the RS232 Test app:

[
 {"name":"CONNECT",         "rx":"A0 04 00 03 43 4F 4E E5",             "tx":"A1 05 00 02 4F 4B A2"},
 {"name":"PAYMENT_REQUEST", "rx":"A0 01 *", "tx":"", "amountStart":4, "amountEnd":-1},
 {"name":"PAYMENT_TYPED",   "rx":"A0 06 *", "tx":"", "amountStart":5, "amountEnd":-1},
 {"name":"PRODUCTION_OK",   "rx":"A0 03 00 07 53 55 43 43 45 53 53 E7", "tx":""},
 {"name":"PRODUCTION_FAIL", "rx":"A0 03 00 06 46 41 49 4C 45 44 A6",    "tx":""},
 {"name":"CANCEL",          "rx":"A0 08 00 06 43 41 4E 43 45 4C A8",    "tx":""}
]
  • "A0 01 *" — the trailing * matches any number of remaining bytes, so one rule catches every amount length.
  • "amountStart":4 — the ASCII amount begins at byte 4 (after Start, CMD and the 2-byte Length). For CMD 06 it starts at 5, because a payment-type byte comes first.
  • "amountEnd":-1 — end is exclusive and negative counts from the frame end, so -1 means "everything up to, but not including, the last byte" — the CRC never pollutes the amount.
  • CONNECT auto-replies OK instantly from the rule itself; payment replies are sent by your code after the charge (next section).

Bench mode — complete rx → tx table. For end-to-end machine testing with no app code at all, give the payment rules a full reply hex too: every receive frame then gets its send frame instantly. This auto-approves every payment (it never charges anyone), so it is for the bench, not production:

[
 {"name":"CONNECT",         "rx":"A0 04 00 03 43 4F 4E E5",             "tx":"A1 05 00 02 4F 4B A2"},
 {"name":"PAYMENT_REQUEST", "rx":"A0 01 *", "tx":"A1 02 00 07 53 55 43 43 45 53 53 E7", "amountStart":4, "amountEnd":-1},
 {"name":"PAYMENT_TYPED",   "rx":"A0 06 *", "tx":"A1 02 00 07 53 55 43 43 45 53 53 E7", "amountStart":5, "amountEnd":-1},
 {"name":"PRODUCTION_OK",   "rx":"A0 03 00 07 53 55 43 43 45 53 53 E7", "tx":"A1 05 00 02 4F 4B A2"},
 {"name":"PRODUCTION_FAIL", "rx":"A0 03 00 06 46 41 49 4C 45 44 A6",    "tx":"A1 05 00 02 4F 4B A2"},
 {"name":"CANCEL",          "rx":"A0 08 00 06 43 41 4E 43 45 4C A8",    "tx":"A1 05 00 02 4F 4B A2"}
]

The payment reply hexes, precomputed (CRC included): SUCCESS = A1 02 00 07 53 55 43 43 45 53 53 E7 · FAILED = A1 02 00 06 46 41 49 4C 45 44 A6. The protocol document defines no reply for production results and CANCEL, but the table acks them with the reader's OK frame (A1 05 00 02 4F 4B A2) so a machine that expects one is satisfied — if the vendor confirms strict firmware that rejects undefined frames, set those tx back to "". This bench table ships preloaded in the RS232 Test app.

3 · The payment flowWho sends what, when

Direction
Frame
machine →
A0 04 00 03 43 4F 4E E5
"CON" — connect. Rule CONNECT auto-replies below, zero code.
→ reader
A1 05 00 02 4F 4B A2
"OK" — sent automatically by the rule's tx.
machine →
A0 01 00 06 31 35 30 30 30 30 A3
payment request 1500.00 — vendRequestListener fires with price=150000. Charge the customer now.
→ reader
A1 02 00 07 53 55 43 43 45 53 53 E7
payment result — your code sends sendXorAscii("A1 02", "SUCCESS") (or "FAILED" → A1 02 00 06 46 41 49 4C 45 44 A6).
machine →
A0 03 00 07 53 55 43 43 45 53 53 E7
production result ("SUCCESS" / "FAILED") — the machine reports after making the coffee. Rules PRODUCTION_OK / PRODUCTION_FAIL ack with the OK frame, log it, and reach your exchangeListener (FAILED = refund the charge).
machine →
A0 08 00 06 43 41 4E 43 45 4C A8
"CANCEL" — machine cancels the payment. Abort the charge.

Multi-payment machines use CMD 06 instead of 01: the first data byte is the payment type (01 transfer, 02 QR, 03 NFC, 04 swipe), then the ASCII amount — A0 06 00 07 01 31 35 30 30 30 30 A4. Rule PAYMENT_TYPED extracts the same price=150000; read the type byte from the frame in your listener. If the reader must return display content (a QR code), answer with CMD 07: sendXorFrame("A1 07", "02 " + Rs232Lib.asciiHex(content)).

4 · App codeThe whole integration

Rs232Lib.setRulesJson(rulesJsonAbove)          // once - persisted across restarts
Rs232Lib.setCrcCheck(true)                     // discard bad-CRC frames (persisted)
Rs232Lib.open(baud = 9600)                     // defaults 8-N-1

Rs232Lib.vendRequestListener = { price, frame ->
    // price = 150000 for 1500.00; frame tells you CMD 01 vs 06
    thread {
        val paid = chargeCustomer(price)       // your gateway
        Rs232Lib.sendXorAscii("A1 02", if (paid) "SUCCESS" else "FAILED")
    }
}

Rs232Lib.exchangeListener = { e ->
    // every frame: e.rxHex, e.ruleName (PRODUCTION_OK, CANCEL...), e.txHex, e.price
}

Verified without hardware: all frames above were fed through Rs232Lib.simulateFrame(hex) — matching, price extraction (150000 and a shorter 3500 frame), the CONNECT auto-reply, and buildXorFrame("A1 02", asciiHex("SUCCESS")) producing byte-identical A1 02 00 07 53 55 43 43 45 53 53 E7. The RS232 Test app's SIMULATE RX button runs the same check on the CM30.
