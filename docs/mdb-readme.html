MDB on the CM30 - the complete guide to hardware-lib

hardware-lib 8.2.15 + mqtt-lib 2.8.0 + dashboard 8.2.13, 16 November 2026. Package com.rabbah.mdb, singleton HardwareLib. This document is the one place that explains what the library does on the MDB bus, every function it exposes, every setting and payload you can configure, and how the dashboard, the backend and the Android app reach it. The per-topic guides (VENDLISTENER-README.md, CANCEL-FLOW-README.md, SESSION-ENDED-README.md, IMPLEMENTATION-README.md, API-REFERENCE.md, PULSE-README.md, RS232 guide) go deeper on one subject each; the release notes (RELEASE-NOTES-8.2.x.md) say what changed when.

1. What this is

The CM30 payment terminal sits inside a vending machine as MDB Cashless Device #1 (address 0x10). The machine's controller (the VMC, the bus master) polls the reader many times per second; the reader may only answer, never speak first. hardware-lib is that reader:

  • it opens the CM30's MDB slave port through the vendor AAR (CM30-HardwareLibrary-1.0.9.aar, armeabi-v7a only),
  • runs the MDB cashless state machine (setup handshake, enable/disable, session, vend, cancel, end),
  • answers every frame inside the MDB reply window on its own bus thread,
  • turns the vend into three app callbacks (onVendRequest, onVendSuccess, onVendFailure) on a separate ordered thread so the app can take a payment and tell the machine to dispense,
  • keeps every reply payload, setting and switch configurable and persisted per machine,
  • and exposes everything (log, status, settings, counters, remote commands) to the dashboard and the Rabbah backend through mqtt-lib, without containing any networking itself.

No networking in hardware-lib, no MDB in mqtt-lib. The only place the two meet is attachRabbahMqtt(), called by mqtt-lib itself on connect.

3.3 A normal vend, step by step

VMC                               reader (hardware-lib)                 app
POLL ---------------------------> BEGIN SESSION (funds FF FF)
VEND REQUEST price item --------> ACK                                   onVendRequest(amount, minorUnits, item)
POLL ---------------------------> ACK (waiting)                         ... take the payment ...
                                                                        approveVend()
POLL ---------------------------> VEND APPROVED price
(dispenses)
VEND SUCCESS item --------------> ACK                                   onVendSuccess(item)   -> capture
SESSION COMPLETE ---------------> ACK
POLL ---------------------------> END SESSION                           (state ENABLED; auto mode re-arms BEGIN SESSION after the cooldown)

If the app calls cancelVend() instead, or the machine sends VEND CANCEL / READER CANCEL, the next POLL carries the cancel-mode reply (SESSION CANCEL REQUEST or VEND DENIED) and the app gets onVendFailure(reason). If the machine answers VEND FAILURE after approval the app gets onVendFailure(FAILED) and must void. If the session ends with the vend still open the app gets onVendFailure(SESSION_ENDED). Every request ends in exactly one of success / failure.

3.4 Threads

  • Bus thread: reads frames from the vendor port, decides the reply, writes it. Nothing else runs here.
  • Offload thread: log lines, listeners, control lines.
  • Vend delivery thread (one, ordered): the three VendListener callbacks. A callback is never delivered before the previous one returned; the vend event gap and the cancel grace are applied here. A callback running longer than 3 s logs a warning and counts in callbackStuck. Exceptions are caught and counted (callbackThrew).

The app must return from the callbacks immediately and do gateway work on its own thread.

What each MDB setting is for:

  • Session mode. Auto: the reader arms BEGIN SESSION as soon as the machine enables it and again after every END SESSION, so the customer can select first and pay after (the usual vending flow). Manual: a session only starts on beginSession(), the "card tap first" flow. Switching mid-session cancels the session.
  • Auto-begin cooldown. Idle POLLs to let pass after END SESSION before re-arming BEGIN SESSION. Sielaff sends READER ENABLE after its first POLL; 3 keeps the two from colliding.
  • MDB level. Decides the level byte in READER CONFIG DATA, which setup step ends INACTIVE, which Peripheral ID payload (30 or 34 bytes) is sent and which Begin Session payload (SESSION_BEGIN for L1, SESSION_BEGIN_L2 for L2/3) is sent. Set it to what the machine's config menu says.
  • Cancel mode. What cancelVend() sends and how the machine's own VEND CANCEL is answered: SESSION CANCEL REQUEST (machine answers SESSION COMPLETE, reader sends END SESSION) or VEND DENIED (session stays open).
  • Direct vend. For machines that send VEND REQUEST without a proper handshake / session; the request is accepted from any state. Also reports ENABLED while the bus is INACTIVE/DISABLED so the app UI shows "ready".
  • Force session end. For machines that never send SESSION COMPLETE after a vend: SESSION CANCEL REQUEST goes out after every VEND SUCCESS so the session closes.
  • Session-cancel retry. When the machine ignores a SESSION CANCEL REQUEST, resend it after the wait, up to the count, then a WARNING. Stops on SESSION COMPLETE, END SESSION, RESET or a new VEND REQUEST.
  • Cancel grace. A customer who presses cancel within 200 ms of the selection would otherwise produce a request and a failure the app renders in the same frame, leaving a stuck screen. The failure is held 500 ms.
  • Vend event gap. Minimum spacing between two callbacks reaching the app, in order, so an app that animates each event never receives the next one mid-animation.
  • Warm resume. After the app restarts (or dashboard Close/Open) the machine is still ENABLED and only sends READER ENABLE / POLL, never RESET; without this the reader stays INACTIVE forever (UNHANDLED rx=14 01 loop).
  • Skip 00 00 vend. Some machines send 13 00 00 00 ... continuously until an item is chosen; the empty requests are ACKed and dropped.
  • MQTT log lines. Whether plain log lines leave the device. Control lines and coded exchanges always flow.
  • Visibility switches. Debug only: idle POLL/ACK, unhandled commands, other peripherals' traffic, empty auto-mode session cycles.

9. How the pieces connect

 vending machine ==MDB bus== CM30 vendor AAR == HardwareLib ==VendListener== Android app (payment, UI)
                                                    |  attachRabbahMqtt()
                                                 mqtt-lib 2.8.0
                                      /            |              \
                      <prefix>/<id>/logs    <prefix>/<id>/ops   <prefix>/<id>/cmd + /passthrough
                      coded MDB items       plain lines +       commands in (backend / dashboard)
                      for the backend       control lines       <prefix>/<id>/status: retained online/offline
                                                 |
                                    Hardware Dashboard (Electron, Windows / macOS)
  • mqtt-lib owns the broker link (MQTT 3.1.1, TCP), retained presence on status, the coded log envelope (RabbahLog), the two inbound command topics and the ops channel. It knows nothing about MDB. On connect it reflectively calls HardwareLib.attachRabbahMqtt().
  • The app (MdbMqttBridge.kt in the demo app, or the RN module react-native-mdb 1.5.0) sets the listeners, calls init, start, and approveVend / cancelVend from the payment result. Backend machine-settings keys (section 5) are applied through the same setters.
  • The dashboard (dashboard-app/, v8.2.13) subscribes to logs + ops, renders the live log, state, settings switches (session mode, cancel mode, level, direct vend, force end, retry, cancel grace, event gap, warm resume, skip 00 00), the Config panel for the 13 payloads, the Vend (stats) button, and the passthrough bar.

11. Testing without a machine

  • simulateExchange("13 00 01 86 00 33") pushes a VEND REQUEST frame (price 390, item 51) through the classify, template and log / exchange listener pipeline on the calling thread, so the dashboard shows code 121. It does not run the state machine, so the VendListener does not fire; to exercise the listener without a machine use RS232 rules with event (see LISTENERS-README.md section 12 and VENDLISTENER-README.md section 8).
  • The JVM bus-trace harness in source/MdbSlaveApp/hardware-lib/bus-trace/ (team BusTrace.java S1-S8 + extra/BusTraceExtra*.java S9-S28) runs the real HardwareLib class against a fake MdbSlave and asserts replies, callbacks and counters for every flow above (stale approve, cancel grace, event gap, warm resume, cash sale, …), S29-S31 (machine ready). All 31 scenarios pass on 8.2.15. run.sh inside builds and runs it.
  • Nothing from 8.1.0 onward has yet run on a real CM30; the dashboard "Verify after deploy" rows in each release note are the field checklist.

12. Known limits

  • SETUP and EXPANSION commands arriving in ENABLED or VEND_STATE are not answered (UNHANDLED).
  • No timeout for a vend that gets neither VEND SUCCESS nor VEND FAILURE after approval (the machine's own 232 s applies on its side only).
  • The vendor AAR is armeabi-v7a only; on any other device start() returns false and only simulateExchange works.
  • The machine-setup template does not yet have fields for cancel grace, event gap and warm resume.
