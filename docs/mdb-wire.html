MDB communication with the VMC, byte by byte, and every configuration file

hardware-lib 8.2.15, 16 November 2026. This document is the wire-level reference: what the vending machine controller (VMC) sends, what the reader answers, every byte of every frame, the handshake per feature level, every session and vend sequence with real checksums, the timing rules, and then every file and store that configures the reader (payload bytes, settings, RS232 rules, backend keys, build-time properties, the dashboard and the setup template). MDB-README.md is the overview, LISTENERS-README.md explains how frames become app callbacks, API-REFERENCE.md lists the functions.

Everything here is taken from MdbSlaveWrapper.kt (bytes and checksum), HardwareLib.kt (the state machine), MdbConfigStore.kt (payloads), MdbSettings.kt (settings) and Rs232Lib.kt (rules).

---

1. The bus in one page

factvalue
rolesthe VMC is the master and talks first; the reader (hardware-lib on the CM30) only answers
our addressCashless Device #1, 0x10. Frames for other peripherals (first byte outside 10-17) are ignored
physical layer9600 baud, 9-bit (mode bit marks the address byte); handled entirely by the vendor libmdbSlave.so; the library sees plain bytes
block sizeat most 36 bytes on the wire: up to 35 data bytes plus the checksum
checksum (CHK)8-bit sum of all preceding bytes, carry discarded, appended as the last byte. Not a CRC. Example from the spec: 11 01 05 DC 00 64 sums to 0x157, CHK 57
ACKa single bare byte 00 sent through sendAnswer(0x00); no CHK. NAK / RET likewise
what the library receivesthe full frame including the VMC's CHK, e.g. 13 05 00 FA 00 00 12: 13+05+FA = 0x112 so CHK 12. A bare POLL is 12 12, a RESET 10 10
what the library sendsACK as the bare byte, or a payload from MdbConfigStore plus a CHK computed in withChecksum() at send time
reply windowa few milliseconds. The bytes go out before anything is logged or formatted; the log line is produced afterwards on another thread
vend decision windowthe reader declares a 232 s max response time, so the VMC keeps polling while the app takes the payment

2. Every VMC command: bytes in, bytes out

CHK is always the last byte. Prices and items are 16-bit big-endian. Item numbers are -1 in the callback when the VMC omits them.

3. Every reply payload, byte by byte

The 13 payloads live in MdbConfigStore. The defaults below are what ships; section 7.1 says how to change them. Bytes marked runtime are overwritten at send time, so editing them in the store has no effect.

3.1 READER CONFIG DATA (8 bytes, reply to SETUP CONFIG)

Default 01 02 19 78 01 02 E8 0B, sent as 01 <level> 19 78 01 02 E8 0E CHK.

bytedefaultmeaning
001reply code
102feature level, runtime = the mdbLevel setting (1, 2 or 3)
2-319 78country / currency code, ISO 4217 numeric with a leading 1: 1978 = 978 = EUR. For Saudi riyal (682) set 16 82
401scale factor; prices on the bus are multiplied by it
502decimal places; with scale 1 and 2 decimals, raw 350 = 3.50
6E8application maximum response time, seconds: 232
70Bmiscellaneous options, runtime = 0E: bit 1 multi-vend, bit 2 reader has a display, bit 3 reports cash sales, bit 0 (refunds to the media) clear

Bytes 4 and 5 are also what priceToAmount and priceToMinorUnits use, so the app and the VMC always agree on the scale. The wire CHK for the default at Level 2 is 8D (Level 1 8C, Level 3 8E).

3.2 PERIPHERAL ID (30 bytes at Level 2, 34 at Level 3, reply to EXPANSION REQUEST ID)

READER_CONFIG_INFO default: 09 43 41 53 30 30 30 30 30 30 30 30 30 30 30 31 30 30 30 30 30 30 30 30 30 30 30 31 00 01, CHK 63.

bytesdefaultmeaning
009reply code
1-343 41 53manufacturer code, ASCII CAS
4-1530 x11 31serial number, ASCII 000000000001
16-2730 x11 31model number, ASCII 000000000001
28-2900 01software version, BCD 00.01
30-33 (L3 only)00 00 00 00optional feature bits Z31-Z34, MSB first. All zero = no optional feature claimed. Bit 5 of byte 33 (Z34) = Always Idle; the engine reads it live

READER_CONFIG_INFO_L3 is the same with the four feature bytes appended; the two are stored separately so switching levels never loses either.

3.3 BEGIN SESSION (reply on a POLL when a session is armed)

namedefaultbyteswireused at
SESSION_BEGIN03 FF FF1-35 editable03 FF FF 01Level 1
SESSION_BEGIN_L203 FF FF 00 00 00 01 00 00 001-35 editable03 FF FF 00 00 00 01 00 00 00 02Level 2 and 3

Layout of the long form: 03 code, FF FF funds available (FFFF = unknown / unlimited), 00 00 00 01 payment media id, 00 payment type, 00 00 payment data. If the bus shows more bytes than 03 FF FF after BEGIN SESSION, the level is 2 or 3 and the long payload is being sent; edit it or set the level to 1.

4. What a POLL gets, in priority order

In VEND_STATE the reader answers the POLL with the first of these that is armed:

  1. END SESSION (endSessionPending): state -> ENABLED, every flag cleared, auto mode re-arms BEGIN SESSION after the cooldown, open vend -> onVendFailure(SESSION_ENDED).
  2. SESSION CANCEL REQUEST or VEND DENIED (sessionCancelPending, per pendingCancelResponse); the retry timer is armed for SESSION CANCEL REQUEST.
  3. VEND APPROVED at the requested price (vendApprovePending && vendRequestReceived).
  4. a due SESSION CANCEL REQUEST retry.
  5. ACK (idle).

In ENABLED_STATE: BEGIN SESSION when armed (auto mode after READER ENABLE or after the cooldown, manual mode after beginSession()), else ACK. In INACTIVE: JUST RESET on up to 5 POLLs after a RESET, then ACK. A stray END SESSION (after a SESSION COMPLETE outside a session) is answered in any state without changing it.

5. Sequences with real bytes

Every frame below includes its CHK. -> is VMC to reader, <- reader to VMC.

5.1 Power-up handshake, Level 1

-> 10 10                        RESET                     <- ACK            state INACTIVE
-> 12 12                        POLL                      <- 00 00          JUST RESET (up to 5 times)
-> 11 00 01 10 02 01 25         SETUP CONFIG (L1 VMC)     <- 01 01 19 78 01 02 E8 0E 8C   READER CONFIG DATA
-> 11 01 02 3F 00 64 B7         SETUP MAX/MIN 575 / 100   <- ACK            state DISABLED
-> 14 01 15                     READER ENABLE             <- ACK            state ENABLED, BEGIN SESSION armed (auto)
-> 12 12                        POLL                      <- 03 FF FF 01    BEGIN SESSION, state VEND_STATE

5.2 Power-up handshake, Level 2 (default)

-> 10 10                                      <- ACK                       INACTIVE
-> 12 12                                      <- 00 00                     JUST RESET
-> 11 00 02 10 02 01 26                       <- 01 02 19 78 01 02 E8 0E 8D
-> 11 01 02 3F 00 64 B7                       <- ACK                       still INACTIVE
-> 17 00 <29 bytes of VMC id> CHK             <- 09 43 41 53 30 ... 31 00 01 63   PERIPHERAL ID, state DISABLED
-> 14 01 15                                   <- ACK                       ENABLED
-> 12 12                                      <- 03 FF FF 00 00 00 01 00 00 00 02   BEGIN SESSION, VEND_STATE

5.3 Power-up handshake, Level 3

Same as Level 2 with 01 03 … 8E as the config data, the 34-byte Peripheral ID (09 … 00 01 00 00 00 00 63), and one more step before DISABLED:

-> 17 04 <4 option bytes> CHK                 <- ACK                       state DISABLED

5.4 A paid vend

-> 12 12                        POLL                 <- 03 FF FF 00 00 00 01 00 00 00 02   BEGIN SESSION
-> 13 00 01 86 00 33 CD         VEND REQUEST 390/51  <- ACK                 onVendRequest(3.90, 390, 51)
-> 12 12 (repeating)            POLL                 <- ACK                 the app is at the gateway
                                                                            app: approveVend()
-> 12 12                        POLL                 <- 05 01 86 8C         VEND APPROVED 390
   (the machine dispenses)
-> 13 02 00 33 48               VEND SUCCESS item 51 <- ACK                 onVendSuccess(51)
-> 13 04 17                     SESSION COMPLETE     <- ACK
-> 12 12                        POLL                 <- 07 07               END SESSION, state ENABLED
-> 12 12 x3                     POLL                 <- ACK                 auto-begin cooldown
-> 12 12                        POLL                 <- 03 FF FF …          next session

5.5 The machine cancels (customer pressed cancel), cancel mode SESSION CANCEL REQUEST

-> 13 00 01 86 00 33 CD         VEND REQUEST         <- ACK                 onVendRequest
-> 13 01 14                     VEND CANCEL          <- ACK                 onVendFailure(CANCELLED_BY_VMC)
-> 12 12                        POLL                 <- 04 04               SESSION CANCEL REQUEST
-> 13 04 17                     SESSION COMPLETE     <- ACK
-> 12 12                        POLL                 <- 07 07               END SESSION

With cancel mode VEND DENIED the POLL gets 06 06 instead and the session stays open for another request.

5.6 The app declines

-> 13 00 …                      VEND REQUEST         <- ACK                 onVendRequest
                                                                            app: cancelVend()  -> onVendFailure(CANCELLED_BY_APP)
-> 12 12                        POLL                 <- 04 04 (or 06 06)

5.7 Dispense failure after approval

-> 12 12                        POLL                 <- 05 01 86 8C         VEND APPROVED
-> 13 03 16                     VEND FAILURE         <- ACK                 onVendFailure(FAILED): refund
-> 13 04 17 / 12 12             SESSION COMPLETE     <- ACK / 07 07

5.8 Force session end (machines that never send SESSION COMPLETE)

-> 13 02 00 33 48               VEND SUCCESS         <- ACK                 onVendSuccess; SESSION CANCEL REQUEST armed
-> 12 12                        POLL                 <- 04 04
-> 13 04 17                     SESSION COMPLETE     <- ACK
-> 12 12                        POLL                 <- 07 07

If the machine ignores the 04 04, the session-cancel retry re-sends it after the wait (default 1000 ms), up to the count (default 3), then logs a warning and stops.

5.9 Reader cancel from the machine, session end with the vend open, reset mid-vend

-> 14 02 16   READER CANCEL in VEND_STATE   <- 08 08   CANCELLED; onVendFailure(CANCELLED_BY_VMC); cancel reply next POLL
-> 14 00 14   READER DISABLE in VEND_STATE  <- ACK     next POLL 07 07 END SESSION; onVendFailure(SESSION_ENDED) if open
-> 10 10      RESET in VEND_STATE           <- ACK     INACTIVE; onVendFailure(RESET); JUST RESET on the next POLLs

5.10 Warm resume (the reader restarted, the machine did not)

-> 14 01 15   READER ENABLE in INACTIVE, no RESET since start()   <- ACK   state ENABLED (8.2.13), BEGIN SESSION armed
-> 12 12                                                           <- 03 FF FF …

Before 8.2.13 this was UNHANDLED and the machine repeated 14 01 every ~150 ms forever.

5.11 Direct vend and Always Idle

With direct vend ON, or at Level 3 with bit 5 of Z34 set, a VEND REQUEST arrives without BEGIN SESSION:

-> 13 00 01 86 00 33 CD   VEND REQUEST in ENABLED (or any state with direct vend)   <- ACK   state VEND_STATE, onVendRequest
-> 12 12                  POLL after approveVend()                                   <- 05 01 86 8C

5.12 Cash sale and revalue

-> 13 05 00 FA 00 00 12   CASH SALE 250, item 0   <- ACK            any state, logged, vendStats cashSales
-> 15 00 00 64 79         REVALUE REQUEST 100     <- 0E 0E          REVALUE DENIED
-> 15 01 16               REVALUE LIMIT REQUEST   <- 0F FF FF 0D    REVALUE LIMIT AMOUNT

7. Every configuration file and store

7.1 Reply payloads: mdb_config

Android SharedPreferences, file /data/data/<app package>/shared_prefs/mdb_config.xml, one string per payload name, value = space-separated hex. A name that is absent, unparsable or of the wrong length falls back to the library default at init(). Lengths are locked except SESSION_BEGIN and SESSION_BEGIN_L2 (1-35 bytes). The checksum is never stored; it is computed at send time.

Ways to read and change it (all equivalent, all live on the next send, all persisted):

7.3 RS232 rules: rs232_rules

SharedPreferences file shared_prefs/rs232_rules.xml: rulesJson (the rule array as loaded) and crcCheck (bool, default false). Restored by init(). The frame gap (frameGapMs, default 1000, remote rs232Gap:MS) is not persisted. At most 20 rules; first match wins.

One rule:

fieldmeaning
namelabel used in the log and the coded event
rxspace-separated hex to match; ?? = any one byte; trailing * = any remaining bytes (since 7.10.0); leading * = match the end of the frame (8.2.3)
txhex to send back; "" = match, report and fire the event, send nothing
priceHi, priceLobyte indexes of a binary price (hi*256 + lo); negative counts from the end, -1 = last byte
amountStart, amountEndstart (inclusive) and end (exclusive) indexes of an ASCII digit price; amountEnd: -1 skips a trailing CRC byte
eventvendRequest (needs a price), vendSuccess, vendFailure, vendCancel: drives the same VendListener as MDB

Loaded with {"setRs232Rules":[…]} (dashboard RS232 panel, backend or Rs232Lib.setRulesJson), read back with getRs232Rules -> RS232_RULES_JSON:[…], cleared with clearRs232Rules.

7.7 Dashboard

The Hardware Dashboard keeps its broker settings (F2: host, port, user, password, topic prefix, device) locally in its Electron user-data folder and writes its log files to <userData>/logs. It sends everything above through the passthrough topic and reads logs + ops. It has no configuration file of its own to ship with the library.

7.8 Machine setup template (docs/machine-setup-template.html)

The form an installer fills per machine: protocol (MDB / RS232 / pulse), feature level, cancel mode, pulse mode (high / low), up to three ready-feedback channels (rf0-rf2, channel = expected value), and the RS232 rule table (rule name, machine sends, we reply, price hi / lo, amount start / end, event). "What gets stored" lists the backend keys of section 7.5 that the form produces. Fields for cancel grace, event gap and warm resume are not yet on it; they keep their defaults unless set from the dashboard or the backend.
